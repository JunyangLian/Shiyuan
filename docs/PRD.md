# 自维护本地知识工作台｜项目需求与技术设计（PRD + Architecture）

**工作代号**：拾源
**版本**：v0.1｜2026-11-20
**目标平台**：Windows 10/11，单用户、本地优先
**文档状态**：产品规划稿；"目标"不代表已实现或已验证的性能
**核心主张**：你的文件按原来的方式保存，知识库自己生长。

## 0. 执行摘要

本项目不是再做一个笔记编辑器、文件上传型 RAG 或通用 Agent，而是为个人、研究生与小型实验室提供一个无须迁移文件、无须持续人工整理、可长期维护的本地知识工作台。用户只需授权现有文件夹，即可获得跨文件搜索、带来源的知识问答和只读数据调查；软件自动发现新增、修改、移动及失联文件，以低成本分级解析、修复索引，并将历史证据与当前有效信息区别呈现。

**首要价值排序**：找得到 → 不过时 → 有来源 → 少打扰 → 成本可控。

**战略取舍**：不追求功能总量超过 Obsidian、Everything、RAGFlow 等成熟产品；优先验证在"真实文件持续变化、用户基本不维护"的环境中，能否以更少的操作保持可靠检索。第一版是 Windows 单机产品，未来才扩展 NAS、远程 Linux、多人权限和团队部署。

## 1. 用户、场景与待验证需求

### 1.1 目标用户

| 优先级 | 用户 | 典型数据 | 核心困难 |
| --- | --- | --- | --- |
| P0 | 研究生、科研助理、技术个人 | 论文、Word、PDF、Excel、代码、实验记录 | 不记得位置；历史版本混乱；懒得维护知识库 |
| P1 | 课题组资料负责人、小型实验室 | 多届学生遗留资料、共享盘、项目交付物 | 数据交接困难、重复文件多、索引经常过时 |
| P2 | 小型咨询/设计/研发团队 | 客户资料、合同、项目记录和附件 | 多来源资料检索、权限与审计 |

### 1.2 三个必须跑通的用户旅程

**旅程 A：找回历史资料。** 用户授权 `D:\科研资料`、`E:\论文`，输入"去年那份 BLAST 结果表"。系统优先返回文件卡片、原始路径、相关片段和打开文件动作；不强制进入聊天。

**旅程 B：半年不管理依然可用。** 用户持续新增、修改、重命名文件，软件在获得运行机会后自动增量同步；检索不会悄悄使用已撤权或确认过时的内容。

**旅程 C：历史结论不一致。** 用户询问某项目样本量，系统展示"计划数、实际采集数、最终分析数"的不同证据与适用阶段；证据不足时说明不确定，不强行选择一个数字。

### 1.3 关键假设（必须实测，不预设成立）

1. 用户确实不愿为 RAG 手动上传、分类、重建知识库。
2. "原位索引 + 自动维护"可以减少人工操作，而不显著牺牲检索召回。
3. 文件搜索与来源引用的使用频率高于复杂自主 Agent 操作。
4. 分级解析能在同等质量约束下降低初次构建或维护成本。
5. 小型实验室愿意在其数据上进行试用，且隐私和资源消耗满足要求。

## 2. 市场定位与竞品策略

| 类别 | 代表 | 应承认的强项 | 我们验证的差异点 |
| --- | --- | --- | --- |
| 笔记知识管理 | Obsidian | Markdown 编辑、链接、生态 | 不要求用户主动组织笔记；原有异构文件直接成为知识源 |
| 本地知识检索 | Miyo、AnythingLLM | 文件连接、索引、AI 问答 | 文件长期变化后的维护负担、失效证据和失败自修复 |
| RAG 平台 | RAGFlow、Dify | 文档解析、检索和编排 | 单机免部署、连接原文件、日常零维护体验 |
| Windows 搜索 | Everything | 快速文件名/路径定位 | 文件内容语义、来源证据、跨文档问答 |
| 自动文档归档 | Paperless-ngx | OCR、标签、归档流程 | 保留用户原位目录，不要求吸纳为归档存储 |

**定位语**："不需要整理文件的本地知识工作台"。
**不宣称**：首创原位索引、首创自动同步、首创本地 RAG。竞品是否在特定动态数据集上存在明显不足，需要验证。

**竞争原则**：当现成产品已满足用户需求时优先复用；新研发只集中于连续维护、异构资产目录、证据有效性、低成本解析调度与用户体验。

## 3. 产品原则

1. **零迁移**：原始文件不复制、不挪动、不重命名；默认只读。
2. **搜索优先**："找文件"比"问一段文字"更常用时，应直接返回可打开的文件。
3. **可渐进使用**：L0 文件目录就绪即可文件名搜索，不等待全部 OCR 完成。
4. **最小打扰**：自动修复低风险问题；复杂冲突保留证据，高风险操作才需要确认。
5. **不静默编造**：呈现来源、文件版本、解析覆盖与不确定性。
6. **本地优先**：默认不上传原始内容、片段或 Embedding；云端调用须明确授权。
7. **权限先于缓存**：当前无权访问的文件，其派生缓存不能因已索引而继续暴露。
8. **可撤销**：用户能移除数据源、清除对应缓存、关闭后台服务、查看维护日志。
9. **省心而不失控**：Agent 先只读调查；写入、移动、删除原件必须另行授权、预览和审批。

## 4. 功能范围与版本优先级

### 4.1 P0 / Windows MVP（首个可试用版本）

| 模块 | 必须交付 | 验收重点 |
| --- | --- | --- |
| 安装与首次启动 | Windows 安装包、无需另装 Python/数据库、可选托盘运行 | 新用户完成安装、授权文件夹、首次搜索 |
| 数据源管理 | 添加/暂停/移除多个本地文件夹，包含/排除规则，只读授权 | 绝不越过授权范围 |
| 资产目录 | 文件名、路径、格式、大小、修改时间、位置与内容版本 | 可定位、可追踪变化 |
| 变更同步 | 监听 + 定期对账；重启后补扫；失联/离线区分 | 不能悄悄返回旧证据 |
| 轻量解析 | PDF 文本层、TXT/MD、DOCX；代码文本；Excel 表头/工作表信息 | 初始覆盖广且成本低 |
| 搜索 | 文件名/路径/元数据 + 全文；基础相关性排序 | 未接 LLM 也能找文件 |
| 基础问答 | 可选在线 API/本地模型，引用文件和位置 | 有证据才回答，允许拒答 |
| 按需 OCR | 扫描 PDF/图片可进入深度任务队列；显示覆盖状态 | 不能假装已经全文检索 |
| 自动维护 | 失败重试、缓存过期重建、任务日志与资源限额 | 用户无需手动重建索引 |
| 隐私设置 | 默认本地索引、联网单独授权、缓存清理 | 外发边界清楚 |

### 4.2 P1 / 形成可测差异化

- 低质量解析检测与自动复核：乱码、空提取、疑似版面顺序错误、图片未识别。
- 按查询需求提升特定文档或页面的解析深度，并验证是否改善检索。
- 近重复文件与版本候选分析，自动提出关系但不擅自认定"终稿"。
- 只读数据管理 Agent：如重复文件报告、项目资料清单、缺失交付物候选。
- 带原文引用的跨文档比较；用户纠正与范围化偏好记录。
- 解析器/Embedding/检索策略版本化，支持安全回滚与重建。

### 4.3 P2 / 团队与生态

- NAS/SMB、远程 Linux、SFTP、对象存储连接器。
- 多用户项目授权、共享工作空间、服务端执行与审计。
- 可配置的 Evidence Ledger，存储实体、属性、时间、条件与来源关系。
- MCP/插件 API，让 Codex、Claude Code 等调用本地知识服务。
- 适配科研格式（FASTA、BAM、VCF）的专业元数据读取器。
- 本地/云端分布式 Worker 和团队备份策略。

### 4.4 明确不做（首版非目标）

- 全功能 Markdown 编辑器、白板、日历或项目协作套件。
- 自动删除、移动、重写用户原始文件。
- 把 BAM/FASTQ 等大型二进制文件全文转 Markdown。
- 基于文件名或 LLM 猜测，自动确定哪份论文或报告是唯一权威版本。
- 复杂企业 RBAC、多租户 SaaS 或通用 RAG 工作流编排平台。

## 5. 核心交互设计

### 5.1 首次使用

1. 安装启动：清楚解释"原件不迁移、默认本地处理"。
2. 选择 1—3 个目录，可设置排除项和索引模式（省资源/平衡/高质量）。
3. 立刻开始 L0 目录扫描，显示文件发现数量和覆盖状态。
4. L1 文本索引按资源预算逐步完成；搜索可尽早使用。
5. 用户直接搜索；深度任务后台继续处理。

### 5.2 主界面

- **统一搜索（默认）**：搜索文件名、路径、内容；结果可筛选文件类型、目录、时间和状态。
- **知识对话**：内部检索，未来可选外部公开资料；两类证据分别标识。
- **数据源**：授权目录、同步状态、排除规则、暂停/取消授权。
- **健康与维护**：最近成功同步时间、解析覆盖率、异常、预算和少量待确认项。
- **设置**：本地/线上模型、隐私策略、CPU/内存/磁盘限额、缓存生命周期。

### 5.3 搜索结果结构

每条结果展示：文件名、当前位置、类型、修改时间、相关片段、来源页码/段落（如果可得）、索引状态、打开原文件动作。"可定位"与"可检索内容"是不同状态，不能混淆。

## 6. 系统架构（首版）

```
Windows Tauri + React 桌面界面
      │
      ▼
本地 Knowledge Core（Python sidecar / FastAPI 或 IPC）
      ├─ Source Manager：授权范围、目录与连接状态
      ├─ Scanner + Watcher：初次扫描、事件合并、周期对账
      ├─ Asset Catalog：文件身份、路径、版本、权限与状态
      ├─ Parse Scheduler：任务队列、预算、优先级、重试
      ├─ Extractors：文本提取 / 可选 OCR / 表格适配
      ├─ Index Service：FTS / 后续向量索引 / 引用映射
      ├─ Retrieval + Answer：混合召回、证据校验、模型适配
      ├─ Maintenance Engine：发现缺口 → 修复 → 验证
      └─ Audit & Settings：操作记录、缓存策略、安全配置
      │
      ├─ SQLite（元数据、任务、FTS5）
      ├─ 向量索引（MVP 可选独立本地组件）
      └─ %LOCALAPPDATA% 下的派生缓存（MD / 结构映射）

用户文件：D:\ / E:\ 原位只读访问，不进入应用托管目录
```

**技术建议**：Tauri + React 负责桌面体验；Python 负责解析、OCR 与 Agent 生态；SQLite WAL + FTS5 简化部署。中文全文搜索需选择合适的分词或 n-gram 策略；向量检索可在验证确有增益后加入。OCR/视觉模型体积较大，考虑按需下载安装，而不是全部打进首版安装包。

**关键约束**：单机程序并不意味着没有安全风险。本地数据库、缓存、云 API 密钥都需要受控保存；处理不可信文件必须对解析器、子进程和资源使用设限。

## 7. 数据模型：位置、资产、内容不能混为一谈

### 7.1 核心表（建议）

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| sources | 用户授权的目录/数据源 | source_id, root_uri, policy, last_scan_at, health |
| assets | 稳定的逻辑资产标识 | asset_id, kind, created_at, lifecycle |
| asset_locations | 资产的一个或多个出现位置 | location_id, asset_id, source_id, path, native_file_id, availability |
| content_versions | 内容身份与版本 | version_id, asset_id, hash, size, mtime, observed_at |
| parse_artifacts | 文本/结构解析缓存 | artifact_id, version_id, parser_signature, cache_uri, quality |
| chunks | 检索块及定位信息 | chunk_id, artifact_id, text, page, offset |
| index_jobs | 任务与重试 | job_id, asset_id, stage, status, attempts, error |
| maintenance_events | 维护证据和审计 | event_id, type, reason, outcome, timestamp |
| user_decisions | 范围明确的用户纠正 | decision_id, scope, claim, evidence, reversible |

### 7.2 五条设计规则

1. **路径不是主键。** 文件移动后 asset_id 应尽量保持不变。
2. **内容哈希不是业务资产 ID。** 两份字节相同的文件可能属于不同项目和权限范围。
3. **解析缓存依赖"内容版本 + 解析器及配置签名"。** 相同内容才可复用同一解析结果。
4. **索引可以重建。** 原文件、证据定位及状态记录必须完整；缓存可按策略清理。
5. **证据跟随具体版本和访问范围。** 移除授权后，任何相关缓存都不能继续绕过权限提供内容。

## 8. 原位文件追踪与增量同步

### 8.1 识别策略

- 首轮：扫描允许的根目录，登记相对路径、大小、时间、类型；必要时读取 Windows 文件标识。
- 实时：监听新增、修改、移动和删除，合并短时间内重复事件。
- 定期：对授权根目录重新枚举，弥补进程退出、系统休眠、网络盘和事件丢失。
- 同盘改名/移动：优先以事件或稳定的原生 ID 识别。
- 跨盘复制/移动：通过内容哈希及辅助证据提出候选；模糊时不得自动合并。
- 巨型文件：分段指纹或元数据可作为候选筛选，不应被当作完全相同的最终证明；按需计算完整哈希。

### 8.2 文件状态（与索引深度分离）

- `AVAILABLE`：路径有效且有权限；
- `STALE`：检测到文件版本可能变化，相关内容索引等待刷新；
- `OFFLINE`：数据源暂时不可达，不能据此判定删除；
- `MISSING`：经有效数据源扫描确认原位置不在；
- `OUT_OF_SCOPE`：文件已移出授权范围或授权撤回；
- `ERROR`：读取或解析异常。

对 STALE 不得默默给出"当前事实"答案；对 OFFLINE 可在策略允许时展示已缓存历史证据，但必须明确离线及验证时间；对 OUT_OF_SCOPE 应立即停止内容检索，并按保留策略清理派生内容。

**Windows 注意**：首版使用 watchdog + 周期扫描；NTFS USN Journal 可留给优化阶段。符号链接、junction/reparse point、UNC 网络共享都必须重新检查真实路径是否仍落在授权范围内。

## 9. 渐进式索引与缓存策略

| 层级 | 覆盖 | 处理内容 | 用户获得什么 |
| --- | --- | --- | --- |
| L0 目录层 | 全部可访问资产 | 文件名、路径、格式、大小、时间、来源 | 快速找文件，了解有哪些资产 |
| L1 轻量内容层 | 可低成本提取的文档 | 原生文本、标题、基本结构、全文索引 | 内容关键词搜索和初级问答 |
| L2 深度层 | 被需求或质量问题触发的子集 | OCR、复杂表格、图像说明、精确定位、向量检索 | 更全面的召回和可靠引用 |

**初次策略**：普通文本和有文本层的 PDF 尽量完整提取；不要只保存关键词，因为稀有关键词和上下文一旦丢失，查询期可能根本找不到文件。扫描件至少记录"内容未覆盖"的事实，允许后台补齐。

**查询策略**：先检索 L0/L1/已有 L2 → 选择候选 → 验证文件可用、版本及权限 → 仅在必要且预算允许时提升解析层级 → 合并证据回答 → 缓存新结果。

**召回盲区**：若扫描件文件名是 `IMG_001.pdf`，L0 根本不知道其中写了什么。解决办法是设置有限预算的后台 OCR 补扫、按目录与邻近文件关系扩展候选，并允许用户主动指定"对这批文件深入索引"。不能承诺只靠懒加载就实现完整召回。

**缓存键**：`content_hash + parser_version + parser_config + modality`；Embedding 索引还需包含模型与切块策略版本。缓存共享不意味着权限共享。

## 10. 自维护飞轮：触发、决策、验证

### 10.1 三个循环

- **数据循环**：文件事件/对账 → 变更归因 → 增量更新 → 索引一致性验证。
- **质量循环**：空白/乱码/解析失败/证据缺页 → 选择更高质量的解析方法 → 比对结果 → 保留有效版本。
- **使用循环**：明确的未找到反馈、低召回诊断或用户纠错 → 分析索引缺口 → 预算内重新解析 → 用固定问题回归验证。

### 10.2 自动决策表

| 问题 | 默认行为 | 是否打扰用户 |
| --- | --- | --- |
| 文件新增、改名、普通修改 | 自动同步/增量解析 | 否 |
| 解析失败或低质量 | 有限次数重试，必要时升级解析器 | 通常否 |
| 文件离线或失联 | 标记状态、之后重扫 | 仅影响当前任务时提示 |
| 不同文件的说法不一致 | 保留双方证据、注明条件与时间 | 默认否 |
| 判断"哪个是唯一正式版本"证据不足 | 不自动断言或删除旧信息 | 需要时问用户 |
| 删除、移动、重写原始文件 | 不默认执行；先展示影响与审批 | 是 |
| 试图上传敏感片段到云端 | 根据来源策略阻断或征求明确授权 | 是 |

### 10.3 不让飞轮失控

- 维护任务有优先级、每日 OCR/Token/CPU/磁盘预算以及退避重试上限。
- 用户提问失败不能直接被当作"知识缺失"，可能只是问题歧义或回答器失败。
- 新解析结果必须经过覆盖率/引用可用性等校验，不能仅凭 LLM 自评就覆盖旧索引。
- 保存可解释的维护日志：为什么处理、花了多少、修复了什么、是否通过验证。
- 软件退出、休眠或数据源离线后能恢复，而不是丢任务或无限重复执行。

## 11. 搜索、问答与管理 Agent

### 11.1 三种交互模式

- **找文件**：面向定位；优先精准路径、文件名、全文匹配和文件卡片，不必调用 LLM。
- **问知识**：面向综合回答；使用混合检索、重排序、引用定位，区分当前证据、历史证据和未经验证的推断。
- **管理数据**：面向只读调查；Agent 可执行"列出重复候选、统计目录内容、查找疑似缺失结果"等受限工具。

### 11.2 检索可靠性

- 检索前过滤当前授权范围；返回前重新检查结果项权限与版本。
- 不仅返回答案，还要返回可定位到文件版本、页码或片段的引用。
- 索引未完整覆盖时提示"当前搜索范围/覆盖程度"，不要直接断言"没有这个信息"。
- 外部网络检索作为 P1/P2 可选工具，结果与内部证据分区，不能混淆来源。
- 对时间、项目、实验阶段和样本口径不同的数字做上下文比较，而非单纯信任最新文件。

### 11.3 Agent 工具权限

第一版默认提供只读工具：`list_sources`、`search_assets`、`read_snippet`、`inspect_asset`、`find_duplicate_candidates`、`get_sync_health`。禁止任意 shell、任意 SQL 写入及任意文件系统操作。后续增加写操作，必须分层授权、预览影响、记录审计和提供安全恢复路径。

## 12. 安全、隐私与数据治理

1. **明确授权范围**：默认只读取用户主动选择的根目录；敏感系统目录排除；处理快捷方式、符号链接、junction 时防止越界。
2. **云端严格 opt-in**：分开控制云端生成、Embedding、OCR 与遥测；外发片段也视为可能敏感数据。
3. **只读原文件**：服务进程优先采用最小权限；用户审批前不得自行修改原件。
4. **缓存安全**：数据源撤权后停止检索，清理对应派生内容；缓存去重不能导致跨用户/跨范围信息泄露。
5. **第三方文档不可信**：解析时限制子进程、资源和文件格式；文档中出现"请忽略系统指令"等文本不得成为 Agent 指令。
6. **密钥管理**：在线模型 API Key 使用 Windows 安全凭证存储或系统加密方案，不以明文写入日志。
7. **透明控制**：可暂停后台索引、限制联网、查看缓存占用、清空索引和彻底退出托盘服务。

## 13. 非功能要求与验收测试

以下是首版候选目标，需要以测试设备和真实文件构成进行校准，不是当前能力承诺。

| 维度 | 候选验收标准 / 测试 |
| --- | --- |
| 可安装性 | 普通用户无需自行安装 Python、PostgreSQL、Docker |
| 初始可用性 | 授权后 L0 完成即可搜索；解析进度与覆盖显式可见 |
| 变化追踪 | 在 1 万文件样本中模拟新增 100、修改 50、移动/改名 50、删除 20；在完整对账后核对漏检与错配 |
| 不过时 | 被确认修改或撤权的文件不再以"当前有效原文"返回 |
| 文件定位 | 对人工标注目标文件计算 Recall@5 / Recall@10 和首次命中时间 |
| 引用质量 | 检查回答引用与原始版本、页码、文字是否吻合 |
| 维护负担 | 统计每 1,000 次真实文件变化的人工干预次数，同时报告错误率 |
| 资源消耗 | 测量首次索引耗时、峰值内存、CPU、磁盘缓存、后台耗电和模型费用 |
| 自动修复 | 人为造成解析失败、文件失联、事件丢失后，统计自动恢复成功率与重复处理量 |
| 权限安全 | 测试越权路径、junction、撤权缓存、外发阻断和恶意文档指令 |

**北极星指标：无需人工维护的有效检索率。** 定义为在动态文件集上，用户不额外管理知识库的前提下，正确找到目标资产或给出充分证据支持答案的请求比例；必须同时报告拒答率、错误答案率、过时引用率，防止指标被"全拒答"或"静默忽略更新"操纵。

## 14. 对照实验与竞品验证

**基线组**：Everything（文件定位），Obsidian + 合理插件（个人知识管理），Miyo/AnythingLLM（本地 RAG），RAGFlow 或标准全量解析 RAG（可比环境）。重点不是所有产品都比同一种指标，而是各对照组承担相应任务。

**动态数据集**：取得授权的真实文件或合成数据；包含普通文本、扫描件、重复文件、无意义文件名、移动/删除、跨版本冲突、权限撤回以及解析失败。

**实验问题**：

1. 用户从安装到首次找对文件需要几步、多久？
2. 一周持续变更后，旧索引产生多少错误或过期引用？
3. 同等 CPU/磁盘/Token 预算下，渐进式解析能否保持目标召回率？
4. 查询失败后，自维护过程是提高了召回，还是只增加了资源消耗？
5. 普通用户在一段使用期内主动维护了多少次？

必须在报告中记录硬件、文件规模、模型、索引策略、参数与失败案例，避免不公平比较。

## 16. 技术风险与应对

| 风险 | 后果 | 应对 |
| --- | --- | --- |
| 首轮浅索引造成召回盲区 | 用户误以为资料不存在 | 后台补扫、覆盖提示、手动深入扫描入口 |
| Windows 事件丢失/磁盘离线 | 索引与原件失配 | 周期对账、状态分离、重启补偿 |
| 跨目录移动识别错误 | 错误合并不同资产 | 文件 ID + 哈希 + 证据，模糊时不自动合并 |
| OCR/图片解析成本太高 | 电脑卡顿、磁盘膨胀 | 分级解析、预算、热度与质量驱动调度 |
| 旧缓存泄露隐私 | 严重信任损失 | 检索前权限检查、撤权失效、缓存清理 |
| LLM 把历史信息当当前事实 | 错误决策 | 版本/时间/条件引用与不确定性提示 |
| 同时做过多格式和功能 | MVP 久拖不成 | 先常见文本，二进制文件只做元数据 |
| 缺乏真实差异化 | 变成另一款 RAG 前端 | 动态数据集对照、低维护成本作为主指标 |

## 17. 项目完成标准（Definition of Done）

最小产品成功不等于"有一个聊天框并能回答几份 PDF"。必须同时具备：

- [ ] Windows 普通用户能完成安装和首次授权；原文件不搬迁。
- [ ] 文件名、路径及普通文本内容能够跨目录搜索。
- [ ] 新增、修改、改名、删除、程序离线期间变化都能经同步与对账正确反映。
- [ ] 问答结果可打开来源文件，能发现并提示索引不完整与版本过时。
- [ ] 深度 OCR 在受控预算下按需运行，并可复用解析缓存。
- [ ] 用户能暂停、撤销授权、清理缓存，并明确控制云端数据外发。
- [ ] 形成与至少一款同类产品或标准基线的可复现对照报告。
- [ ] 至少完成一轮真实用户试用，记录成功案例、失败案例、人工维护次数和改进需求。

## 18. 待决策清单

在开发前应冻结以下默认选择，允许后续经测试修改：

1. **首发数据范围**：本地 NTFS 文件夹为主；UNC/NAS 暂不承诺实时可靠监听。
2. **首发格式**：PDF（文本层）、DOCX、MD、TXT、代码；Excel 先做轻量结构信息；图片 OCR 按需。
3. **本地模型要求**：基础文件搜索完全离线；AI 问答可以通过用户主动配置的模型运行，不能让无模型用户无法使用基本功能。
4. **索引覆盖策略**：优先全部文件 L0、常见文本 L1、预算内局部 L2；明确展示覆盖率。
5. **首次产品验证对象**：5—10 位拥有真实混乱目录的用户；每人提供若干带标准答案的找文件任务。
6. **暂定产品名称**：上线前核查品牌冲突；不要让命名延误核心原型。

**最终产品承诺（需要通过测试兑现）**：你仍然可以像过去一样存放文件；软件安静地维护一个可以搜索、可以提问、能回到原文、尽量不过时的本地知识层。用户越使用它，系统应越了解哪些信息值得处理，而不是制造更多必须人工维护的知识库任务。
